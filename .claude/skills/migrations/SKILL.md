# Migrations — request, explain, apply

Nothing applies EF migrations in this workspace. `Migrations__RunOnStartup` is `false` in every
local mode, so `aspire run` and standalone `dotnet run` both log *"assuming the schema is already
current"* and then serve a model that may be ahead of the database. The failure surfaces later, as
a runtime `Npgsql.PostgresException` — `42703: column ... does not exist` or `42P01` for a table.

That flag is off on purpose: every environment shares the one DigitalOcean database, and a feature
branch must not be able to migrate it. So the answer to "who applies migrations?" is **a human,
explicitly** — this skill is how that decision gets put to them with enough information to make it.

## Hard rules

- **Never apply anything without an explicit yes in the current turn.** Approval for one migration
  is not approval for the next one.
- **Never set `Migrations__RunOnStartup=true` locally** as a shortcut. That flag being off is the
  only thing stopping any checked-out branch from migrating production's database.
- **Never read `*.Designer.cs`** under `Infrastructure/Persistence/Migrations/` — 1,600–2,000-line
  generated files that will flood context (see the `code-map` skill). The script parses the small
  sibling `.cs` mechanically so those files never enter context. Read a migration `.cs` by hand
  only when the script's classification looks wrong.
- **Report honestly.** If a module errors out, say so — do not report "all current" when one
  context failed to load.

## When to run

| Moment | Why |
|---|---|
| After `gh pr create` on a Backend change | So the branch can be tested against a real schema. A hook nudges you, but it cannot fire for a PR opened in the GitHub web UI — run it yourself then. |
| After the PR merges to main | Catches anything added during review, and is the *only* safe moment for breaking DDL. |
| On a 42703 / 42P01 at runtime | The first thing to rule out. Check this before debugging the C#. |
| On request | "Are there pending migrations?", "did that migration run?" |

## Procedure

**1 — Check.** Cheap, cached, silent when there is nothing to do:

```bash
node .claude/skills/migrations/scripts/migrations.mjs check
```

Exit 0 = every module current, stop here. Exit 1 = pending (or a module failed to load). Exit 2 =
no connection string; `launchSettings.json` is gitignored and must be recreated locally.

**2 — Explain.** Never skip to applying:

```bash
node .claude/skills/migrations/scripts/migrations.mjs explain
```

For each pending migration this prints the verdict, the parsed operations, the commit that
introduced it (subject + rationale), whether that commit is on `main` yet, and **the real DDL** as
generated by `dotnet ef migrations script`.

**3 — Present it to the user.** A short table — module, migration, what it does in plain words,
why (from the commit), and the verdict — then the DDL. The user should not have to read EF output
to decide. State clearly whether the migration is on `main` or feature-branch-only.

**4 — Ask.** See the confirmation rules below. Use `AskUserQuestion` when there is a real choice
to make; a plain question is fine when it is one additive migration.

**5 — Apply,** one module per explicit approval:

```bash
node .claude/skills/migrations/scripts/migrations.mjs apply Trips
```

**6 — Verify.** `apply` re-lists and fails loudly if anything is still pending. Then exercise the
thing that was broken — hit the endpoint, reload the screen. Note that `42703` is a *parse-time*
error, so even a `200 []` on an empty table proves the column resolved.

## Confirmation rules

The script assigns each migration a verdict from its worst operation.

| Verdict | Operations | How to ask |
|---|---|---|
| `additive` | `AddColumn` (nullable, or NOT NULL with a default), `CreateTable`, `CreateIndex`, `AddForeignKey`, `EnsureSchema` | Plain yes/no. Deployed code ignores a column it does not select. Safe pre-merge. |
| `no-op` | empty `Up()` — history row only | Plain yes/no. Mention it changes no schema. |
| `review` | `AlterColumn`, `Sql`, `InsertData`/`UpdateData`/`DeleteData`, `DropIndex` | Show the DDL and say what it touches. Raw `Sql` is unparsed — read it before asking. |
| `breaking` | `DropColumn`, `DropTable`, `Rename*`, `Drop*Constraint`, or `AddColumn` NOT NULL with no default | **Hard warn.** Name what currently-deployed code the change breaks, and refuse to apply without an explicit override in that turn. |

**Breaking migrations on a feature branch: do not apply.** The `explain` output marks each
migration `on main` or `NOT on main`. A drop or rename applied from an unmerged branch breaks main
and production the moment it runs, and the PR might still change. Say so, and offer to apply after
merge instead. If the user overrides after being told, that is their call — proceed and say what
you applied.

An `AddColumn` that is NOT NULL with no default is classified breaking on purpose: Postgres rejects
it outright on a non-empty table, so it is additive in name only.

## Commands

| Command | Purpose |
|---|---|
| `check [--force]` | Pending check. Cached on the set of migration filenames; `--force` bypasses. |
| `explain [--json]` | Full request: verdict, ops, provenance, real DDL. Never cached. |
| `apply <Module>` | `dotnet ef database update` for one module, then re-verify. Clears the cache. |
| `classify <file>` | Parse one migration `.cs` and print ops + verdict. No database, no `dotnet`. |
| `pr-hook` | PostToolUse payload on stdin; wired in `.claude/settings.json`. |

Modules are discovered from `Backend/src/*/Infrastructure/Persistence/*DbContext.cs` — currently
Billing, Budgeting, Clients, Drivers, Fleet, Identity, Notifications, Trips. Each owns its own
`__EFMigrationsHistory`, so they are always checked and applied per module.

## Notes

- The connection string is read from the gitignored
  `Backend/src/Api/NorthernLink.Api/Properties/launchSettings.json` — the only place it exists on a
  dev machine. All captured output is scrubbed of secret values before it is printed, so `dotnet
  ef` error text cannot leak the password into a log or into context.
- `check` uses `--no-build`. If a module reports *"run `dotnet build` in Backend/ first"*, build and
  re-run rather than treating it as current.
- A full check across all eight modules takes about six seconds.
- `ModuleMigrationRunner` (`Backend/src/Shared/Persistence/Migrations/`) is the deployed-container
  path for the same job, under one advisory lock. This skill is the local/dev path; they never run
  at the same time because the flag is off locally.
